# EasyAdmin — Техническое задание

> **Статус:** реализовано (см. `README.md`). Итоговый стек отличается от предложенного в §5 ради простоты самостоятельного развёртывания: Node.js 22 без внешних зависимостей, встроенный `node:sqlite`, фронтенд на чистом JS без сборки. Реализованы также роли admin/operator/viewer с доступом по панелям, 2FA, уведомления (Telegram/webhook), планировщик, шаблоны и клонирование, вебхуки CI, инвентарь образов и сертификатов, история нагрузки, бэкап и метрики. Также реализованы SSO (OIDC), email-уведомления (SMTP) и потоковые логи сервисов (WebSocket панели → SSE; путь WebSocket не документирован и настраивается через `EASYPANEL_LOGS_PATHS`). Все функции проверены на имитации Easypanel; совместимость с реальной панелью проверяется командой `npm run probe`.

Единая веб-консоль для управления несколькими панелями [Easypanel](https://easypanel.io) через их API.

## 1. Цель и назначение

Сейчас каждый сервер с Easypanel управляется в отдельном интерфейсе. EasyAdmin — центральный сервис, в котором администратор:

- добавляет подключения к панелям (URL + API-токен);
- видит состояние всех серверов, проектов и сервисов в одном месте;
- выполняет полный набор операций над сервисами любой подключённой панели без перехода в её UI;
- делегирует доступ команде с разграничением прав и ведёт аудит действий.

### Не входит в MVP
Биллинг, мобильное приложение, собственная система деплоя (используется деплой Easypanel), управление самим хостом (SSH).

## 2. Роли и сценарии

| Роль | Возможности |
|---|---|
| Owner | Всё, включая управление пользователями и подключениями |
| Admin | Управление подключениями и сервисами на назначенных панелях |
| Operator | Деплой, старт/стоп/рестарт, просмотр логов, env (без удаления) |
| Viewer | Только чтение (статусы, метрики, логи) |

Ключевые сценарии:
1. Добавить панель: ввести URL и API-токен → проверка соединения → панель появляется в списке.
2. Дашборд: сводка по всем панелям (онлайн/офлайн, число проектов/сервисов, CPU/RAM/диск).
3. Открыть панель → проект → сервис; выполнить действие (deploy, restart, stop, правка env, домены, монтирования и т.д.).
4. Массовые операции: перезапустить/задеплоить выбранные сервисы на нескольких панелях.
5. Клонирование/перенос конфигурации сервиса между панелями (шаблоны).
6. Просмотр журнала аудита и уведомления о сбоях.

## 3. Функциональные требования

### 3.1 Управление подключениями
- CRUD подключения: имя, URL, токен, теги/группы, заметки.
- Тест соединения (health-check) при создании и по расписанию (раз в 1–5 мин).
- Токены хранятся зашифрованными (AES-256-GCM, мастер-ключ из окружения/KMS), в UI и логах никогда не показываются повторно.
- Поддержка самоподписанных сертификатов (опция per-connection, по умолчанию выключена).
- Статусы: online / offline / auth_error / degraded; время последней успешной проверки.

### 3.2 Управление ресурсами Easypanel (через API панели)
- **Проекты:** список, создание, удаление.
- **Сервисы** (app, postgres, mysql, mariadb, mongo, redis, compose и др. — по фактическому API):
  создание, просмотр, изменение настроек, удаление.
  - Действия: deploy, start, stop, restart, rebuild, destroy.
  - Источники: Git, Docker-образ, Dockerfile, Nixpacks/Buildpacks.
  - Env-переменные (просмотр/редактирование, маскирование секретов, импорт/экспорт .env).
  - Домены и прокси, порты, монтирования (volume/bind/file), ресурсы (лимиты CPU/RAM).
  - Мониторинг и статистика контейнера; логи (стриминг/tail).
  - Бэкапы БД, если поддерживается API.
- **Панель/система:** версия, настройки, пользователи панели, Docker-ресурсы, очистка (prune), обновление — насколько доступно через API.
- Полнота покрытия определяется OpenAPI/tRPC-схемой Easypanel (см. §8, риск R1).

### 3.3 Агрегация и UX
- Глобальный поиск по сервисам, доменам, проектам всех панелей.
- Фильтры по панели/тегу/статусу/типу сервиса.
- Единый дашборд с живым статусом (polling + SSE/WebSocket).
- Тёмная/светлая тема, адаптивность.

### 3.4 Автоматизация
- Массовые действия с прогрессом по каждой цели и отчётом.
- Шаблоны сервисов (сохранить конфиг → развернуть на другой панели).
- Планировщик: рестарты/деплои по расписанию.
- Webhooks и уведомления (Telegram, email, Slack): падение панели/сервиса, неудачный деплой.

### 3.5 Безопасность и аудит
- Аутентификация: email+пароль (argon2id), TOTP 2FA, опционально OIDC/SSO.
- RBAC на уровне панелей (и опционально проектов).
- Аудит: кто, когда, какую панель/сервис, какое действие, результат; неизменяемый журнал; экспорт.
- Rate limiting, CSRF-защита, строгие cookie, CSP.
- Секреты не попадают в логи; маскирование в ответах API.

### 3.6 Собственный API
- REST/JSON API EasyAdmin (OpenAPI) + персональные API-ключи для автоматизации.

## 4. Нефункциональные требования

| Область | Требование |
|---|---|
| Производительность | Дашборд на 50 панелей / 1000 сервисов грузится < 2 с (из кэша) |
| Надёжность | Недоступность одной панели не влияет на остальные (таймауты, circuit breaker, retry с backoff) |
| Масштабирование | Stateless бэкенд, воркеры для фоновых задач |
| Безопасность | OWASP ASVS L2, шифрование секретов at-rest, TLS обязателен |
| Развёртывание | Docker-образ, docker-compose, шаблон для деплоя в самом Easypanel |
| Наблюдаемость | Структурные логи, метрики Prometheus, health/readiness эндпоинты |
| Локализация | RU и EN |

## 5. Архитектура

```
Browser (SPA) ──HTTPS──► EasyAdmin API ──► PostgreSQL (пользователи, подключения, аудит, шаблоны)
                              │  ├──────► Redis (кэш, очереди, pub/sub)
                              │  └──────► Worker (health-check, sync, bulk, scheduler)
                              ▼
                    Easypanel Client (адаптер, версионирование)
                              ▼
                    Панели 1..N (Easypanel API + токен)
```

Рекомендуемый стек (можно скорректировать на этапе 0):
- **Backend:** TypeScript, Node.js, Fastify/NestJS; Zod-схемы; клиент к Easypanel — типизированная обёртка (tRPC/HTTP) с версионными адаптерами.
- **Frontend:** React + Vite + TanStack Query + shadcn/ui.
- **БД:** PostgreSQL + Drizzle/Prisma; **очереди:** BullMQ (Redis).
- **Тесты:** Vitest, Playwright (e2e), mock-сервер Easypanel для интеграционных тестов.
- **CI/CD:** GitHub Actions (lint, typecheck, test, build, docker push).

### Модель данных (основное)
- `users`, `sessions`, `api_keys`, `roles/permissions`
- `panels` (id, name, url, token_enc, tls_insecure, tags, status, last_seen, panel_version)
- `panel_access` (user ↔ panel ↔ role)
- `cache_entities` (снимок проектов/сервисов для быстрого поиска)
- `audit_log`, `jobs`/`bulk_operations`, `templates`, `notification_channels`, `schedules`

## 6. Пошаговый план разработки

Оценка ориентировочная для 1–2 разработчиков.

### Этап 0 — Исследование и фундамент (1 нед.)
1. Изучить API Easypanel: способ авторизации (API-токен), список эндпоинтов, схемы, версионирование, потоковые данные (логи/статистика). Зафиксировать в `docs/easypanel-api.md`.
2. Развернуть тестовую панель, снять реальные запросы/ответы, собрать фикстуры.
3. Утвердить стек, структуру репозитория (monorepo: `apps/api`, `apps/web`, `packages/easypanel-client`, `packages/shared`).
4. Настроить CI, линтеры, форматирование, pre-commit, docker-compose для разработки.

**Результат:** документ API, каркас репозитория, зелёный CI.

### Этап 1 — Ядро: клиент Easypanel и подключения (1–2 нед.)
1. Пакет `easypanel-client`: авторизация, типизированные методы чтения (проекты, сервисы, статусы), таймауты, ретраи, нормализация ошибок.
2. Mock-сервер Easypanel + контрактные тесты.
3. БД, миграции, шифрование токенов.
4. API: CRUD подключений, тест соединения, health-check воркер.
5. UI: список панелей, форма добавления, индикаторы статуса.

**Результат:** можно добавить панель и увидеть её статус.

### Этап 2 — Аутентификация и RBAC (1 нед.)
1. Регистрация первого владельца (setup wizard), логин, сессии, 2FA (TOTP).
2. Роли и права на панели, middleware проверки.
3. Приглашения пользователей, управление ими в UI.

**Результат:** защищённый доступ, разграничение прав.

### Этап 3 — Просмотр ресурсов и дашборд (1–2 нед.)
1. Синхронизация проектов/сервисов в кэш (фоновая + по запросу).
2. UI: дашборд, дерево панель → проект → сервис, карточка сервиса.
3. Метрики и статус контейнеров, просмотр логов (стриминг через SSE).
4. Глобальный поиск и фильтры.

**Результат:** read-only консоль по всем панелям.

### Этап 4 — Управление сервисами (2–3 нед.)
1. Действия: deploy/start/stop/restart/rebuild/destroy с подтверждениями и опасными зонами.
2. Редактирование настроек: источник, env, домены, порты, монтирования, ресурсы.
3. Создание проектов и сервисов (мастер по типам).
4. Управление БД-сервисами и бэкапами (по возможностям API).
5. Аудит всех мутирующих действий; учёт прав.
6. e2e-тесты ключевых операций против mock/тестовой панели.

**Результат:** полноценное управление, паритет с основными функциями UI Easypanel.

### Этап 5 — Массовые операции и автоматизация (1–2 нед.)
1. Очередь задач, bulk-операции с прогрессом и частичными ошибками.
2. Шаблоны и клонирование сервисов между панелями.
3. Планировщик (cron-задачи).
4. Уведомления (Telegram/email/Slack/webhook).

**Результат:** операции в масштабе, оповещения о сбоях.

### Этап 6 — Публичный API, безопасность, наблюдаемость (1 нед.)
1. OpenAPI-документация, персональные API-ключи.
2. Аудит-просмотр и экспорт, rate limiting, security-заголовки, pen-test чек-лист.
3. Prometheus-метрики, структурные логи, алерты.

### Этап 7 — Релиз (1 нед.)
1. Нагрузочное тестирование (50 панелей / 1000 сервисов), оптимизация.
2. Документация: установка, обновление, бэкап/восстановление, руководство пользователя.
3. Публикация Docker-образа, шаблон для Easypanel, CHANGELOG, версия 1.0.

**Итого:** ~9–13 недель до 1.0. MVP (этапы 0–3 + базовые действия из этапа 4) — ~5–6 недель.

## 7. Критерии приёмки

- Панель добавляется по URL и токену; неверные данные дают понятную ошибку.
- Токены не видны ни в UI, ни в логах, ни в API-ответах; в БД лежат зашифрованными.
- Все действия из §3.2, доступные в API Easypanel, выполнимы из EasyAdmin.
- Падение одной панели не блокирует работу с остальными.
- Каждое мутирующее действие фиксируется в аудите; права ролей соблюдаются (покрыто тестами).
- Покрытие тестами: unit ≥ 70 % ядра, e2e на основные пользовательские сценарии.
- Развёртывание одной командой `docker compose up` и через шаблон Easypanel.

## 8. Риски

| # | Риск | Митигация |
|---|---|---|
| R1 | API Easypanel недокументирован/нестабилен, меняется между версиями | Слой адаптеров с версионированием, контрактные тесты, фиксация версии панели, фича-флаги |
| R2 | Часть функций UI Easypanel недоступна через токен | Раннее исследование (этап 0), явная матрица поддерживаемых функций |
| R3 | Утечка токенов панелей = полный контроль над серверами | Шифрование, 2FA, аудит, минимальные права, ротация мастер-ключа |
| R4 | Медленные/недоступные панели тормозят UI | Кэш, таймауты, circuit breaker, фоновые синхронизации |
| R5 | Расхождение состояния кэша и реальности | Инвалидация после действий, периодический sync, кнопка «обновить» |
