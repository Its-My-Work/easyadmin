# EasyAdmin — ТЗ: 5 ключевых функций роста (Roadmap v1.0)

> **Статус:** проект (draft для реализации). **Базовая версия:** 0.9.0. **Цель:** сделать EasyAdmin самым удобным self-hosted «пультом» для Easypanel-серверов и получить органический рост звёзд на GitHub за счёт функций, которые одновременно (а) заменяют 2–3 сторонних сервиса, (б) красиво выглядят на скриншоте/GIF, (в) не требуют ни одной новой зависимости.

## 1. Архитектурный манифест и единые стандарты

### 1.1 Неизменяемые принципы

| # | Принцип | Следствие для реализации |
|---|---|---|
| P1 | **0 runtime-зависимостей** | Только `node:*`. HTTP-клиент — `globalThis.fetch`; SSE — ручной парсер `ReadableStream`; SVG-бейджи — шаблонные строки; Telegram/Discord/OpenAI — чистый `fetch`. Любой PR с `dependencies` в `package.json` отклоняется. |

| P3 | **Безопасность по умолчанию** | Все новые функции **выключены**, пока администратор явно их не включил. Опасные действия — только из белого списка (§1.3). |
| P4 | **Совместимость данных** | Только аддитивные миграции (новые таблицы / `ALTER ... ADD COLUMN`). Никаких `DROP`/`RENAME`. Откат версии не ломает БД. |
| P5 | **Тестируемость** | Логика — в чистых функциях без DOM/сети; сеть и хост подменяются через DI (`fetchImpl`, `runOnHost`-стаб) как уже сделано в `createAlerts`. Покрытие новых модулей — `node --test`. |
| P6 | **Мультиязычность** | Каждая строка UI и уведомлений — в `i18n-dict.js` для **6 языков** (RU, EN, ZH, DE, ES, PT). Нет строки — сборка тестов падает (тест полноты словаря). |
| P7 | **6 тем** | Только CSS-переменные тем (`var(--bg)`, `var(--fg)`, …); никаких хардкод-цветов, кроме семантических статусов. Публичная страница поддерживает `prefers-color-scheme` + выбор темы. |

### 1.3 Единый реестр действий (`src/actions.js`) — ядро безопасности

Фичи 1, 3, 4, 5 исполняют действия на серверах. Чтобы не плодить «ручки с root», вводится **единый реестр действий** — белый список, в котором каждое действие описано кодом:

```js
// пример записи
'service.restart': {
  risk: 'low',                       // low | medium | high
  roles: ['admin', 'operator'],      // кто может вызывать
  params: { panelId: 'int', project: 'name', service: 'name' }, // строгая схема
  run: (ctx, p) => manager.runAction(...),   // через API Easypanel
  audit: 'service.restart',
}
'host.journal_vacuum': { risk: 'medium', roles: ['admin'], params: { size: 'enum:100M|200M|500M|1G' }, run: runOnHostScript(...) }
```

Правила:

1. **Команды хоста формируются только кодом** из шаблонов; пользовательский/LLM-ввод **никогда** не конкатенируется в shell. Параметры проходят валидацию по схеме (`int`, `name` = `/^[a-z0-9][a-z0-9._-]{0,62}$/i`, `enum`, `path` — нормализованный, без `..`, внутри разрешённых корней).
2. Каждое действие пишет запись в `audit` (`action`, `target`, `ok`, `detail`) — включая действия, инициированные из Telegram/Discord/AI (`username = 'telegram:<chat>'` / `'ai-doctor:<user>'`).
3. Каждое действие имеет `risk`. `high` требует **подтверждения** (повторный ввод пароля/TOTP в UI либо вторую кнопку «Подтвердить» в мессенджере с TTL 60 с).
4. Действие, выполненное через EasyAdmin, вызывает `alerts.expect(panelId, label)` — чтобы не получать алерт на собственное действие (механизм уже есть).
5. Долгие/разрушительные хост-операции запускаются **отдельным transient-юнитом** `systemd-run --collect --unit=ea-<id>` (хост-оболочка живёт в docker-контейнере и умирает вместе с Docker — см. комментарий в `host-exec.js`); результат читается опросом `systemctl show`/`journalctl -u`.

### 1.4 Единые стандарты безопасности

| Область | Требование |
|---|---|
| **Секреты** | API-ключи LLM, токены ботов, секреты вебхуков хранятся шифрованно (`encrypt(key, …)` из `crypto.js`, как `channels.config_enc`). В API и логах отдаются только маскированно (`sk-…a1b2`). |
| **Токены одноразовые** | Генерация `crypto.randomBytes(24)` → base64url; в БД только `sha256`-хэш; сравнение `timingSafeEqual`; TTL; атомарное «погашение» (`UPDATE … WHERE used_at IS NULL`, проверка `changes === 1`). |
| **Публичные эндпоинты** | Только `GET`/`HEAD`, без cookie, без CORS-credentials; ответы **не содержат** внутренних URL, имён проектов, IP, токенов — только то, что админ явно отметил как публичное (whitelist-модель). |
| **Заголовки** | `SECURITY_HEADERS` + для `/status` отдельная CSP: `default-src 'none'; style-src 'self'; img-src 'self' data:; script-src 'self'; connect-src 'self'; frame-ancestors 'none'` (опционально `frame-ancestors *` по флагу embed). |
| **SSRF** | Исходящие запросы к LLM/вебхукам: только `http(s)`, запрет `file:`/`gopher:`; для облачных провайдеров — блок приватных диапазонов, **кроме** явно разрешённого флага «локальный провайдер» (Ollama на `127.0.0.1`/docker-сеть). Редиректы — не следовать (`redirect: 'manual'`). |
| **Лимиты** | Размер тела запроса ≤ 1 МБ (`readJson`); размер контекста LLM ≤ настроенного; таймауты на каждый исходящий вызов (`AbortSignal.timeout`). |
| **Аудит** | Любое мутирующее действие и любая выдача/погашение токена — в `audit`. |
| **RBAC** | Ролевая модель (`admin`/`operator`/`viewer`) и `user_panels` соблюдаются всегда: действие над панелью допустимо, только если `canPanel(user, panelId)`. Для действий из мессенджера роль привязана к **каналу** (см. §6.5). |

### 1.5 Единые стандарты перформанса

| Метрика | Бюджет |
|---|---|
| Доп. RAM фоновых задач | ≤ 25 МБ на весь набор новых функций в простое |
| Доп. CPU в простое | < 1 % одного ядра; все периодические задачи — один общий тик (переиспользуем `scheduler.js` / интервал опроса `pollIntervalMs`) |
| Публичный `/status` | p95 ≤ 20 мс из кэша; **0 запросов к панелям и БД на горячем пути** (рендер из in-memory снимка, пересборка раз в N секунд) |
| БД | Новые таблицы с индексами под запросы; ретенция и агрегация (§7); `PRAGMA journal_mode=WAL` уже включён |
| Фронтенд | Новые модули подгружаются лениво (`await import()`) — не раздувают стартовый бандл; публичная страница ≤ 30 КБ без сжатия (HTML+JS+CSS) |
| Сетевые потоки | SSE с `Cache-Control: no-store`, `X-Accel-Buffering: no`, heartbeat-комментарий раз в 15 с, отмена при `req.on('close')` (отмена исходящего запроса к LLM через `AbortController`) |

## 2. Фича 1 — AI Doctor

### 2.1 Суть и ценность

Кнопка **«🩺 Диагностика»** на странице сервиса, в карточке упавшего контейнера и в алерте. Один клик → EasyAdmin собирает контекст (логи, метрики, события, состояние) → маскирует секреты → отправляет в LLM → **потоком** показывает разбор: **причина**, **вердикт** (серьёзность), **пошаговое решение** и, если решение сводится к безопасному действию из реестра (§1.3), — кнопку **«Применить»**.

«Вау»-эффект: пользователь видит стриминговый ответ и одну кнопку вместо часа чтения логов.

### 2.2 Провайдеры (OpenAI-compatible)

Единственный протокол — `POST {baseUrl}/chat/completions` (OpenAI-compatible). Это покрывает: OpenAI, **OmniRoute**, **Ollama** (`http://host:11434/v1`), **DeepSeek**, LM Studio, vLLM, OpenRouter, Groq, Together и любой совместимый прокси.

Настройка профиля провайдера (`ai_providers`, §7):

| Поле | Описание |
|---|---|
| `name` | Отображаемое имя («Ollama локальный», «DeepSeek») |
| `base_url` | Например `https://api.deepseek.com/v1`, `http://ollama:11434/v1` |
| `api_key_enc` | Шифрованный ключ (может быть пустым для Ollama) |
| `model` | Идентификатор модели (`deepseek-chat`, `llama3.1:8b`, `gpt-4o-mini`) |
| `max_context_tokens` | Бюджет контекста (по умолчанию 8000) |
| `max_output_tokens` | Лимит ответа (по умолчанию 1200) |
| `temperature` | По умолчанию 0.2 |
| `local` | Флаг «локальный» — разрешает приватные адреса (SSRF-исключение) и отключает предупреждение о передаче данных вовне |
| `extra_headers_enc` | Доп. заголовки (для прокси/OmniRoute), шифрованно |
| `is_default` | Провайдер по умолчанию |

Требования:
- Кнопка **«Проверить подключение»**: запрос `GET /models` (если нет — минимальный `chat/completions` на 1 токен), вывод латентности и найденных моделей (datalist для поля `model`).
- Fallback-цепочка: если основной провайдер вернул 5xx/таймаут — одна автоматическая попытка на следующем по приоритету (опционально, `fallback_of`).
- Ответ модели **никогда не исполняется автоматически**.

### 2.3 Сбор контекста (`ai/collector.js`)

Для цели `panelId + project + service` собирается пакет:

| Источник | Что берём | Лимит |
|---|---|---|
| Логи контейнера | Последние N строк через уже существующий канал логов (WebSocket `serviceLogs`); приоритет строкам уровня `error|fatal|panic|exception|OOM|killed` + 20 строк вокруг каждой | 300 строк / 24 КБ |
| Состояние сервиса | `enabled`, `health`, число реплик, образ и тег, время последнего деплоя, restart count | — |
| Метрики | Из `svc_metrics`: CPU/RAM/сеть за последние 60 мин (агрегат: min/avg/max/p95, тренд) | 12 точек |
| Хост | Из `stats_history`: CPU/RAM/диск панели; опционально (если включён host-exec) `df -h`, `free -m`, `dmesg | tail -n 30 | grep -i oom` | 2 КБ |
| События | Последние записи `audit` по сервису (деплой, рестарт, правка env) за 24 ч — «что менялось перед сбоем» | 10 записей |
| Конфигурация | Список **имён** env-переменных (значения **не** передаются), порты, лимиты ресурсов, healthcheck | — |

**Режимы приватности** (настройка на провайдера): `strict` — только логи и метрики; `standard` — + состояние и аудит; `full` — + хостовые команды. По умолчанию `standard`; для не-`local` провайдеров перед первым запуском показывается явное предупреждение «логи будут отправлены на <host>».

### 2.4 Редактирование секретов (`ai/redact.js`)

Чистая функция `redact(text) → { text, hits }`, применяется **до** кэширования и отправки. Маскируются (заменой на `«[REDACTED:type]»`):

- `Authorization: Bearer …`, `Basic …`, заголовки `X-Api-Key`, `Cookie`, `Set-Cookie`;
- пары `KEY=value`/`"key": "value"` где ключ ~ `/(pass(word)?|secret|token|api[_-]?key|private[_-]?key|dsn|credential|auth)/i`;
- URL с учётными данными `scheme://user:pass@host`;
- JWT (`eyJ…\.….…`), PEM-блоки `-----BEGIN … PRIVATE KEY-----`, AWS-ключи (`AKIA[0-9A-Z]{16}`), строки с высокой энтропией ≥ 32 символов base64/hex;
- e-mail и IPv4 — опционально (флаг `redact_pii`, по умолчанию выкл. для IP, т.к. они нужны диагностике).

Тесты: корпус из ≥ 40 реальных фрагментов логов (nginx, postgres, node, python traceback, java stacktrace) — ни один секрет не должен «протечь».

### 2.5 Промпт и формат вердикта

Системный промпт (хранится в коде, версионируется `prompt_version`), язык ответа = язык интерфейса пользователя. Модель обязана вернуть **структурированный блок** в конце ответа (для надёжного парсинга и кнопки применения):

```
<analysis free-form markdown streamed to the user>

```easyadmin-verdict
{"severity":"critical|warning|info","cause":"OOM-kill: контейнер превысил лимит 256 МБ",
 "confidence":0.82,
 "fixes":[{"title":"Увеличить лимит памяти до 512 МБ","action":"service.set_memory","params":{"limitMb":512},"risk":"medium"},
          {"title":"Перезапустить сервис","action":"service.restart","params":{},"risk":"low"}]}
```
```

Правила разбора:
- Блок ищется по ограждению ` ```easyadmin-verdict `; JSON валидируется схемой; невалидный → показывается только текстовый разбор, без кнопок.
- `fixes[].action` **обязан** присутствовать в реестре действий (§1.3) и пройти валидацию `params`; неизвестные действия отбрасываются. `panelId/project/service` подставляются **сервером** из контекста запроса, а не из ответа модели.
- Для каждого fix рисуется кнопка **«Применить»** с бейджем риска; `medium/high` — через диалог подтверждения с текстом реальной операции («Будет выполнено: …»).
- Защита от prompt-injection: содержимое логов передаётся в отдельном сообщении роли `user` внутри ограждения `<logs>…</logs>`, системный промпт явно запрещает выполнять инструкции из логов; действия из ответа всё равно проходят белый список + подтверждение человека.

### 2.6 Потоковый SSE-вывод

Эндпоинт возвращает `StreamResponse` (механизм уже есть в `http.js`):

```
POST /api/ai/diagnose            → { id }                    (создаёт задачу диагностики)
GET  /api/ai/diagnose/:id/stream → text/event-stream
```

Типы событий SSE:

| event | data | Когда |
|---|---|---|
| `status` | `{"stage":"collecting"\|"redacting"\|"cached"\|"thinking"}` | этапы пайплайна |
| `context` | `{"lines":212,"redactions":3,"bytes":9120,"provider":"deepseek"}` | прозрачность: что отправлено |
| `delta` | `{"t":"…текст…"}` | чанк ответа (из `choices[0].delta.content`) |
| `verdict` | JSON вердикта (§2.5) | после завершения потока |
| `done` | `{"tokens":{"in":1840,"out":612},"ms":4210,"cached":false}` | конец |
| `error` | `{"code":"provider_timeout","message":"…"}` | ошибка (пользователю — человекочитаемая) |

Реализация провайдера: `fetch(..., { body: JSON.stringify({ stream: true, … }), signal })` → `response.body.getReader()` → разбор строк `data: …` / `data: [DONE]`, буферизация неполных строк, устойчивость к `\r\n`, к чанкам, порванным посреди UTF-8 (`TextDecoder` со `stream: true`). Если провайдер не поддерживает стрим (ответ `application/json`) — один `delta` целиком. Отмена клиента (`close`) обязательно прерывает исходящий запрос.

Фронтенд (`ai-doctor-modal.js`): `fetch` + `ReadableStream` (а не `EventSource`, чтобы передавать CSRF/заголовки), рендер markdown **без `innerHTML` из ответа** — минимальный безопасный markdown-рендерер на `h(...)` (заголовки, списки, `code`, блоки кода, жирный); ссылки не кликабельны, кроме `https`.

### 2.7 Кэширование повторных ошибок

Цель — не платить за один и тот же сбой дважды и мгновенно показывать известное решение.

1. **Отпечаток ошибки** (`fingerprint`): из редактированных логов извлекаются «сигнатурные» строки (уровень ≥ error + первая строка стектрейса), нормализуются (числа → `N`, UUID/хэши/временные метки/порты/пути с id → плейсхолдеры, нижний регистр), сортируются, берутся ≤ 5 уникальных → `sha256(service_image_repo + '\n' + signatures + '\n' + prompt_version + '\n' + lang)`.
2. Таблица `ai_cache` (§7): `fingerprint → response_md, verdict_json, provider, model, hits, created_at, last_hit_at, expires_at`.
3. TTL по умолчанию 7 суток (настройка 1–30), максимум 500 записей (LRU по `last_hit_at`).
4. Попадание в кэш: событие `status:cached` → ответ воспроизводится «печатным» SSE-потоком (имитация стриминга, 40 символов/20 мс) с пометкой **«⚡ из кэша · N раз»**; кнопка **«Перегенерировать»** игнорирует кэш и перезаписывает запись.
5. Кэш не используется, если в контексте сильно отличаются метрики (флаг `oom`/`cpu_high` входит в отпечаток как «профиль метрик»).
6. Анти-шторм: одновременные диагностики с одним отпечатком схлопываются (single-flight): второй клиент подписывается на тот же поток.
7. Бюджет: суточный лимит токенов/запросов на провайдера (`daily_token_limit`), счётчик в `ai_usage`; при превышении — 429 с понятным сообщением.

### 2.8 Точки входа в UI

- Страница сервиса → кнопка «🩺 Диагностика» (вкладка «Логи» и шапка).
- Карточка сервиса со статусом `failing/stopped` на дашборде — иконка-стетоскоп.
- Command Palette: `> doctor <сервис>` (Фича 4).
- Алерт `service_down` (Telegram/Discord): кнопка **«🩺 AI-разбор»** (Фича 5) → ответ приходит ссылкой в UI либо краткой сводкой (≤ 800 символов) в чат.
- Настройки → «AI Doctor»: провайдеры, режим приватности, кэш (статистика попаданий, очистка), лимиты, история диагностик.

### 2.9 Критерии приёмки

- [ ] С Ollama без интернета диагностика работает полностью локально.
- [ ] Первый токен ответа отображается ≤ 1 с после начала генерации у провайдера (EasyAdmin не буферизует).
- [ ] Ни один секрет из тестового корпуса не покидает процесс (e2e с поддельным провайдером, записывающим тело запроса).
- [ ] Повторный сбой того же сервиса отвечает из кэша ≤ 300 мс до первого `delta`.
- [ ] Вердикт с неизвестным `action` не порождает кнопку; кнопка `risk:medium` не срабатывает без подтверждения.
- [ ] Закрытие вкладки обрывает исходящий запрос к провайдеру (проверка по счётчику активных сокетов).

## 3. Фича 2 — Public Status Page

### 3.1 Суть и ценность

Публичная страница `/status` — замена Uptime Kuma/Statuspage для небольших команд: красивая, быстрая, без авторизации, с бейджами для README, инцидентами и историей аптайма за 90 дней. Данные берутся из уже работающего опроса EasyAdmin — **отдельный мониторинг не нужен**.

### 3.2 Модель «публичности» (whitelist)

Ничего не публикуется по умолчанию. Администратор создаёт **компоненты** страницы (`status_components`, §7), каждый — привязка к источнику:

| Тип источника | Проверка |
|---|---|
| `panel` | Статус панели из снимка менеджера (`online/offline/auth_error`) |
| `service` | Состояние сервиса (`enabled`, `health`) на панели |
| `http` | Активная HTTP(S)-проверка URL (метод GET/HEAD, ожидаемый код, подстрока в теле, таймаут ≤ 10 с) |
| `tcp` | Проверка TCP-порта |
| `tls` | Срок сертификата домена (уже есть `tlsProbe`) |
| `manual` | Ручной статус (для плановых работ) |

Для каждого компонента задаётся **публичное имя**, описание, группа, порядок, видимость. Реальные URL/хосты/имена проектов в публичный вывод **не попадают**.

### 3.3 Сбор данных и расчёт аптайма

- Пробер использует общий тик (шаг проверки 30–300 с, по умолчанию 60 с). HTTP-проверки выполняются с ограничением параллелизма (≤ 5), SSRF-политика §1.4 (приватные адреса запрещены, если не включён флаг для конкретной проверки админом), `User-Agent: EasyAdmin-StatusProbe`.
- Состояние компонента: `operational | degraded | partial_outage | major_outage | maintenance`. Переход в `major_outage` — после **N подряд неудач** (по умолчанию 2) и возврат после 1 успеха (защита от флаппинга).
- Хранение: сырые пробы 48 ч в `status_checks`, агрегаты по дням в `status_daily` (`up_seconds`, `down_seconds`, `degraded_seconds`, `checks`, `fails`, `avg_ms`, `p95_ms`) на 400 дней.
- **Аптайм %** = `1 − (down + maintenance×0) / (период − период_плановых_работ)`; плановые работы **не** снижают аптайм; `degraded` учитывается с коэффициентом 0.5 (настраивается). Окна: 24 ч, 7 д, 30 д, 90 д. Формула и округление (до 2 знаков, отображение «99.95 %») — в чистой функции с тестами, включая границы (период без данных → «—», а не 100 %).
- Время простоя ЕasyAdmin самого (процесс не работал) — пробелы в данных, помечаются как «нет данных», а не как простой.

### 3.4 Инциденты и обслуживание

Таблицы `status_incidents`, `status_incident_updates`, `status_maintenance` (§7).

- **Автоматические инциденты**: при переходе компонента в `major_outage` создаётся черновик инцидента (`auto=1`, видимость настраивается: «публиковать сразу» / «после ручного подтверждения»); при восстановлении — закрывается с вычисленной длительностью.
- **Ручные инциденты**: заголовок, затронутые компоненты, статус жизненного цикла `investigating → identified → monitoring → resolved`, серия обновлений с markdown-light (абзацы, списки, ссылки `https`).
- **Плановые работы**: окно `starts_at/ends_at`, компоненты переходят в `maintenance`, анонс за N часов.
- Публикуемые тексты хранятся на языке админа; опционально `title_i18n` JSON для 6 языков (если нет перевода — fallback на основной).
- Каждый инцидент → алерт в каналы (новый тип события `incident_opened/updated/resolved` в `EVENT_TYPES`).

### 3.5 Публичные эндпоинты (без авторизации)

| Путь | Тип | Описание |
|---|---|---|
| `GET /status` | HTML | Страница; серверный рендер первого экрана (быстрый LCP, работает без JS) + прогрессивное улучшение |
| `GET /status/api/summary` | JSON | Общий статус, компоненты, аптайм-окна, активные инциденты/работы |

### 3.6 Кастомизация

Настройки (`settings`, ключи `status_*`): заголовок страницы, описание, **логотип** (PNG/SVG/WebP ≤ 256 КБ, хранится в БД как blob/base64; **SVG санитизируется** — удаляются `<script>`, `on*`-атрибуты, `<foreignObject>`, внешние `href`; отдаётся с `Content-Security-Policy: sandbox` и `Content-Type: image/svg+xml`), favicon, акцентный цвет (валидируется `#rrggbb`), тема (светлая/тёмная/авто — используем набор из 6 тем: выбор «по умолчанию для страницы»), футер, ссылка «Связаться с поддержкой», скрытие «Powered by EasyAdmin» (по умолчанию показывается — ненавязчивый growth-канал), язык по умолчанию (определение по `Accept-Language`, переключатель 6 языков), `noindex`-флаг, **кастомный домен** через `EASYADMIN_PUBLIC_URL`/`Host`-маппинг (`status_host`: если задан, страница отдаётся на корне `/` для этого `Host`).

### 3.7 Защита от DoS и злоупотреблений

1. **Нулевая стоимость запроса**: рендер из in-memory снимка (`status.snapshot`), пересборка по таймеру (5–15 с) и при изменении состояния. Ни одного запроса к БД/панелям на горячем пути.
2. **Кэш и ETag**: сильный `ETag` = хэш снимка; `If-None-Match` → `304`; `Cache-Control: public, max-age=15, stale-while-revalidate=60`; предсжатый `gzip`/`br` (`node:zlib`) кэшируется вместе со снимком.
3. **Rate limit** (`src/rate-limit.js`): token-bucket в памяти по IP (учёт `X-Forwarded-For` только если задан `trustProxy`), `EASYADMIN_STATUS_RPS` (по умолчанию 20/с, burst 40); превышение → `429` + `Retry-After`; глобальный лимит на процесс (защита от распределённой атаки), при его достижении отдаётся устаревший кэш.
4. **Ограничение памяти лимитера**: LRU ≤ 10 000 ключей, TTL записей 60 с.
5. **Жёсткие ограничения парсера**: максимум заголовков/длина URL (встроенные лимиты `node:http` + явные `maxHeaderSize`, `headersTimeout`, `requestTimeout`, `keepAliveTimeout`), отбрасывание тел у GET.
6. **Параметры**: `days ≤ 400`, `limit ≤ 100`, `window ∈ {24h,7d,30d,90d}`, `slug` — по белому списку компонентов. Неизвестное → `404` без различий во времени ответа.
7. **Изоляция**: публичные маршруты — отдельный раннер `publicRouter`, не имеющий доступа к `ctx.user`, сессиям и хост-слою; ошибки не раскрывают стек.
8. **Бейджи**: результат кэшируется по ключу `(slug, metric, window, style)`, число комбинаций ограничено.
9. **Отключаемость**: `EASYADMIN_STATUS=off` → `404` на всех `/status*`; переключатель в UI применяется без рестарта.
10. **Хост-пробы не являются вектором**: публичный посетитель **не может** заставить сервер делать запросы — адреса проверок задаёт только администратор.

### 3.8 UX страницы

Шапка (логотип, название, «Все системы работают» / «Частичный сбой» / «Крупный сбой»), блок активных инцидентов и плановых работ, список компонентов с цветным индикатором и **90-дневной полосой аптайма** (tooltip: дата, % и длительность простоя), аптайм 30/90 д, график времени отклика (SVG, без библиотек), история инцидентов, подписка (Atom), переключатель языка и темы. Доступность: контраст AA, `aria-label` на индикаторах, не только цвет (иконки/текст), полноценная работа без JS.

### 3.9 Критерии приёмки

- [ ] `autocannon`-подобный тест (самописный скрипт на `node:http`): 5 000 rps на 1 vCPU при p95 ≤ 20 мс, RSS не растёт.
- [ ] Страница не содержит ни одного внутреннего хоста/имени (тест-«сниффер» по снимку БД).
- [ ] Остановка тестового сервиса → через ≤ 2 интервала проверки компонент `major_outage`, создан инцидент, ушёл алерт; запуск → автозакрытие.
- [ ] Плановое окно не снижает аптайм; расчёт совпадает с эталонными таблицами тестов.
- [ ] Загрузка SVG с `<script>` и `onload` нейтрализуется.
- [ ] Бейдж отображается в GitHub README (проверка заголовков, размера < 3 КБ).

## 4. Фича 3 — Server Doctor и оптимизация диска

### 4.1 Суть и ценность

Страница **«Server Doctor»** на каждый сервер: оценка здоровья «A–F», список находок и **безопасные рецепты в 1 клик**: вакуум журнала, `docker builder prune`, добавление Swap, диагностика деградации диска и inode. Решает самые частые причины падения Easypanel-серверов («кончился диск», «OOM без swap»).

### 4.2 Транспорт выполнения

Приоритет: (1) `runOnHost` через `/ws/hostShell` панели (по умолчанию, ключи не нужны); (2) SSH (`src/ssh.js`, если для панели настроен ключ — `panels/:id/ssh-key`). Выбор транспорта автоматический, с явным индикатором в UI. Ограничения `runOnHost` (оболочка живёт в Docker) → **любой мутирующий рецепт и всё, что дольше ~20 с, запускается как transient-юнит** `systemd-run --collect --unit=ea-doctor-<id> --property=… sh -c '…'`; статус и вывод читаются отдельными короткими вызовами; Docker-операции (prune) безопасны для запуска в самой оболочке, но выводятся так же через юнит ради единообразия.

### 4.3 Диагностические проверки (только чтение)

Каждая проверка — чистая функция «команда → парсер → находка `{id, severity, title, details, metrics, fixIds[]}`» с тестами на реальных образцах вывода.

| ID | Что проверяет | Команды (константы в коде) | Пороги |
|---|---|---|---|
| `disk.usage` | Заполнение разделов | `df -PT -x tmpfs -x devtmpfs -B1` | warn ≥ 80 %, crit ≥ 90 % |
| `disk.inodes` | Исчерпание inode | `df -Pi -x tmpfs -x devtmpfs` | warn ≥ 80 %, crit ≥ 90 % (даже при свободных байтах) |
| `disk.top` | Что занимает место | `du -xh --max-depth=1 /var /var/lib/docker /var/log 2>/dev/null \| sort -rh \| head -15` (с таймаутом `timeout 20`) | — |
| `docker.df` | Размер образов/контейнеров/томов/билд-кэша | `docker system df --format '{{json .}}'` | reclaimable > 1 ГБ → предложить |
| `docker.logs` | Огромные json-логи контейнеров без ротации | `find /var/lib/docker/containers -name '*-json.log' -size +200M -printf '%s %p\n'` | > 200 МБ |
| `journal.size` | Размер журнала | `journalctl --disk-usage` | > 500 МБ |
| `logs.var` | `/var/log` (старые `*.gz`, `*.1`) | `du -sb /var/log` | > 1 ГБ |
| `apt.cache` | Кэш пакетного менеджера | `du -sb /var/cache/apt` | > 300 МБ |
| `mem.swap` | Нет swap / swap забит | `free -b`, `swapon --show --bytes`, `grep -E 'MemTotal\|SwapTotal' /proc/meminfo` | RAM < 4 ГБ и swap = 0 → warn |
| `mem.oom` | Недавние OOM-kill | `journalctl -k --since '7 days ago' -g 'Out of memory\|oom-kill' --no-pager \| tail -n 20` | ≥ 1 → warn |
| `disk.health.smart` | Деградация диска (SMART) | `smartctl -H -A /dev/<dev>` если `smartctl` установлен (иначе — «не установлен» + кнопка установки через `apt`) | `Reallocated_Sector_Ct`, `Current_Pending_Sector`, `Offline_Uncorrectable` > 0 → crit; `Percentage Used` (NVMe) ≥ 80 → warn |
| `disk.health.kernel` | Ошибки ввода-вывода | `journalctl -k --since '7 days ago' -g 'I/O error\|EXT4-fs error\|XFS.*corrupt\|blk_update_request\|Buffer I/O error' \| tail -n 20` | ≥ 1 → crit |
| `disk.health.fs` | Файловая система смонтирована ro | `findmnt -no OPTIONS /` (содержит `ro`) | crit |
| `disk.io` | Задержки I/O | `cat /proc/pressure/io` (PSI), `iostat -x 1 2` при наличии | `some avg10` > 20 → warn |
| `disk.trend` | Прогноз заполнения | Линейная регрессия по `stats_history.disk` (7–14 дней) | «заполнится через ~N дн.» при N < 14 |
| `sys.updates` | Ожидают обновления безопасности | `apt list --upgradable 2>/dev/null \| grep -c security` | информационно |

Виртуальные/сетевые ФС и `/dev/loop*` исключаются из оценки. Оценка здоровья: старт 100, штрафы за находки (crit −25, warn −10), буква A≥90, B≥80, C≥65, D≥50, F<50.

### 4.4 Рецепты очистки (мутирующие, роль `admin`)

Каждый рецепт: **предпросмотр** (dry-run с оценкой освобождаемого места) → подтверждение с текстом точной команды → выполнение → отчёт «освобождено X МБ» (разница `df`) → запись в `audit`.

| Рецепт | Команда (шаблон из кода) | Риск | Предпросмотр |
|---|---|---|---|
| `journal.vacuum` | `journalctl --vacuum-size=<200M\|500M\|1G>` или `--vacuum-time=<7d\|14d\|30d>` | low | `journalctl --disk-usage` |
| `journal.persist_limit` | Запись `SystemMaxUse=` в `/etc/systemd/journald.conf.d/ea-limit.conf` + `systemctl restart systemd-journald` | medium | показать итоговый файл |
| `docker.builder_prune` | `docker builder prune -f [--filter until=168h]` | low | `docker system df` (строка Build Cache) |
| `docker.image_prune` | `docker image prune -a -f --filter until=<168h>` (только неиспользуемые) | medium | `docker image ls` с фильтром dangling/unused |
| `docker.container_prune` | `docker container prune -f --filter until=<24h>` | medium | список остановленных |
| `docker.volume_prune` | **Не включено по умолчанию.** Только после ввода слова-подтверждения и показа списка томов, с жёстким предупреждением о потере данных | high | `docker volume ls -f dangling=true` |
| `docker.truncate_logs` | `truncate -s 0 <файл>` только для путей, прошедших проверку `^/var/lib/docker/containers/[0-9a-f]{64}/[0-9a-f]{64}-json\.log$` | medium | размер файла |
| `docker.log_rotation` | Запись `/etc/docker/daemon.json` (`log-driver: json-file`, `max-size: 50m`, `max-file: 3`) с **бэкапом и слиянием** существующего JSON; применение требует `systemctl reload docker` / рестарт (предупреждение о рестарте контейнеров) | high | diff файла |
| `apt.clean` | `apt-get clean && apt-get autoremove -y` | low | `du` кэша |
| `logs.rotate_old` | `find /var/log -type f \( -name '*.gz' -o -name '*.[0-9]' \) -mtime +14 -delete` | low | список/объём |
| `swap.create` | см. §4.5 | medium | расчёт размера |
| `swap.remove` | `swapoff /swapfile && rm /swapfile` + чистка `/etc/fstab` | medium | — |
| `swap.tune` | `vm.swappiness=10`, `vm.vfs_cache_pressure=50` в `/etc/sysctl.d/99-easyadmin.conf` | low | текущие значения |
| `smartctl.install` | `apt-get install -y smartmontools` | low | — |

Дополнительно — режим **«Умная очистка в 1 клик»**: последовательность всех рецептов уровня `low` + сводный отчёт; рецепты `medium/high` предлагаются, но не выполняются автоматически.

### 4.5 Добавление Swap в 1 клик

Алгоритм (детерминированный, идемпотентный, отдельный transient-юнит):

1. **Пред-проверки**: `swapon --show` (уже есть swap → показать и предложить `resize`), свободное место (`df -B1 /`), требование `свободно ≥ размер + max(10 %, 2 ГБ)`; тип ФС (`btrfs` → `chattr +C`/`btrfs filesystem mkswapfile`; `zfs` → отказ с объяснением); контейнерная/OpenVZ-виртуализация (`systemd-detect-virt -c`) → предупреждение «swap может быть недоступен».
2. **Рекомендуемый размер**: RAM ≤ 2 ГБ → 2×RAM; ≤ 8 ГБ → 1×RAM; > 8 ГБ → 4 ГБ; пользователь может выбрать 512 МБ … 16 ГБ.
3. **Создание**: `fallocate -l <N> /swapfile || dd if=/dev/zero of=/swapfile bs=1M count=<N>` → `chmod 600` → `mkswap` → `swapon` → идемпотентная запись в `/etc/fstab` (`grep -q '^/swapfile' || echo '/swapfile none swap sw 0 0' >> /etc/fstab`), с резервной копией `fstab.ea-bak`.
4. **Тюнинг**: опциональное применение `swap.tune`.
5. **Проверка результата**: `swapon --show`, `free -m`; откат при ошибке (`swapoff`, удаление файла, восстановление fstab).
6. Прогресс в UI (SSE `GET /api/server-doctor/jobs/:id/stream`), итог «Swap 2 ГБ активен».

### 4.6 Безопасность Server Doctor

- Только команды из каталога (§1.3); ни один путь/значение из тела запроса не попадает в shell без whitelist-валидации и экранирования (одинарные кавычки `'` + замена `'` → `'\''`, плюс строгая регулярка до экранирования).
- Мутирующие рецепты — роль `admin` + `canPanel`; `high` — повторное подтверждение паролем/TOTP.
- Один рецепт на хост одновременно (мьютекс по `panelId`, как очередь `inQueue` в `scheduler.js`).
- Максимальное время выполнения юнита (`RuntimeMaxSec`), лимит вывода 64 КБ.
- Защита от самоповреждения: запрет рецептов, затрагивающих `/var/lib/docker/volumes`, `/etc/easypanel`, `/etc/dokploy`, том данных EasyAdmin; удаление образов не касается образов запущенных контейнеров (Docker это гарантирует, но дополнительно проверяется предпросмотром).

### 4.7 Автоматизация и интеграции

- **Расписание**: рецепты `low` можно ставить в `schedules` (новый `target.type = 'host_recipe'`), например «journal.vacuum 500M по воскресеньям».
- **Алерты**: новые события `disk_inodes_high`, `disk_health_bad`, `swap_missing`, `oom_detected`; интеграция с `disk_high` — в алерт добавляется кнопка **«🧹 Очистить»** (Фича 5), запускающая безопасный набор.
- **AI Doctor**: находки Server Doctor — часть контекста диагностики (Фича 1).
- **Отчёт**: «освобождено за месяц: 12.4 ГБ» (по таблице `doctor_runs`) — виджет на дашборде.

### 4.8 Критерии приёмки

- [ ] На тестовой VM с заполненным на 95 % диском «Умная очистка» освобождает ≥ ожидаемого, сервисы остаются работоспособны.
- [ ] Swap создаётся и переживает перезагрузку; повторный запуск идемпотентен; на btrfs/zfs ведёт себя как описано.
- [ ] Проверка inode обнаруживает искусственно исчерпанные inode при свободных байтах.
- [ ] Попытка выполнить произвольную команду / путь вне whitelist через API → `400`, запись в `audit`.
- [ ] Парсеры проверок покрыты тестами на реальных выводах Ubuntu 22.04/24.04, Debian 12.

## 5. Фича 4 — Command Palette 2.0

### 5.1 Суть и ценность

Превратить палитру `Ctrl+K` из навигатора в **полноценную клавиатурную консоль управления**: всё главное — без мыши. «Linear/Raycast для вашей инфраструктуры».

Сейчас (`palette-order.js`): группы `fav · recent · panel · page · cmd · service`, ранжирование токенов, чистые функции. 2.0 расширяет модель, сохраняя обратную совместимость и тесты.

### 5.2 Режимы и префиксы

Первый символ запроса переключает режим (подсказка видна в поле ввода):

| Префикс | Режим | Пример |
|---|---|---|
| *(нет)* | Универсальный поиск (как сейчас) | `kilo` |
| `>` | **Команды** (действия над сервисом/хостом) | `> restart api` |
| `/` | **Файловый менеджер** — переход к пути | `/ var/log` , `/ ~/backups` |
| `@` | Панели/серверы | `@ prod` |
| `#` | Проекты | `# shop` |
| `!` | Логи | `! api` |
| `?` | Справка/горячие клавиши | `?` |
| `:` | Быстрые числовые/системные (тема, язык, `:theme dark`) | `:lang de` |

### 5.3 Реестр команд (`public/js/palette-commands.js`)

Каждая команда — декларативный объект:

```js
{
  id: 'service.restart',
  title: 'Перезапустить сервис',           // i18n-ключ
  aliases: ['restart', 'rs', 'reboot'],     // для нечёткого поиска и английских/локальных синонимов
  hotkey: 'g r',                            // необязательно
  needs: ['service'],                       // какие аргументы нужны: service | panel | path | text | none
  risk: 'low',                              // low | medium | high → требует confirm
  can: (user, ctx) => …,                    // видимость по роли и контексту
  run: async (args, ui) => …,               // вызов API
}
```

Ввод аргументов — **многошаговый** (Raycast-стиль): выбрали команду «Перезапустить» → палитра переключается в режим выбора сервиса (с тем же ранжированием и нечётким поиском) → `Enter` → подтверждение для `risk ≥ medium` (`Enter` — подтвердить, `Esc` — отмена). Недавно использованные пары «команда+цель» поднимаются выше (usage-frequency, `localStorage`, затухание).

Минимальный набор команд релиза:

| Команда | Действие | Горячая клавиша (аккорд) |
|---|---|---|
| Перезапустить сервис | `service.restart` | `g` `r` |

| Передеплоить | `service.deploy` | `g` `d` |

### 5.4 Горячие клавиши (без мыши)

- Глобальные: `Ctrl+K` / `⌘K` — открыть палитру; `Ctrl+Shift+P` — сразу режим команд (`>`); `?` вне поля ввода — оверлей шпаргалки; `Esc` — назад/закрыть.
- **Аккорды в стиле Vim/GitHub**: `g` затем буква в течение 1.2 с (индикатор «g…» внизу экрана); отключаются в полях ввода, в редакторе кода, в терминале (xterm перехватывает фокус).
- Навигация внутри палитры: `↑/↓`, `Ctrl+N/P`, `Ctrl+J/K`, `PgUp/PgDn`, `Home/End`, `Tab` — автодополнение (подставляет выбранную команду/путь), `Enter` — выполнить, `Shift+Enter` — «альтернативное действие» (например, открыть логи вместо перехода), `Ctrl+1…9` — выбор N-го результата, `Ctrl+Backspace` — стереть слово, `Backspace` в пустом аргументе — вернуться на шаг назад.
- Настраиваемые: переопределение аккордов в Настройках → «Горячие клавиши» (хранится в `settings`/`localStorage`; проверка конфликтов; сброс по умолчанию).
- Доступность: ARIA-паттерн `combobox` + `listbox`, `aria-activedescendant`, фокус-трап, живая область для результатов («12 результатов»), `prefers-reduced-motion`.
- Раскладки: аккорды определяются по `event.code` (физические клавиши), чтобы работали на русской/китайской раскладке; алиасы команд — на всех 6 языках.

### 5.5 Файловый менеджер из палитры

`/` включает режим путей: автокомплит каталогов через `GET /api/panels/:id/files?path=…&dirs=1` (с дебаунсом 120 мс, отменой устаревших запросов `AbortController`, кэшем на сессию), хлебные крошки, закладки (уже есть «быстрые закладки» файлового менеджера — они попадают в выдачу первыми). `Enter` — открыть каталог в `files-page` на выбранной панели; `Shift+Enter` — открыть как файл в редакторе; `Ctrl+Enter` — скачать.

### 5.6 Серверная часть

Палитра не требует новых серверных сущностей, кроме:
- `GET /api/palette/index` — **единый компактный индекс** (панели, проекты, сервисы, закладки ФМ, бэкап-задания, роли) с ETag; обновляется при изменении снимка; позволяет работать с палитрой без десятков запросов.
- Исполнение команд — существующие эндпоинты + `POST /api/actions/run` (единый реестр действий, §1.3) — один вход вместо множества ручек, с аудитом и подтверждением.

### 5.7 Перформанс и качество

- Открытие палитры ≤ 16 мс (кадр); ранжирование 5 000 элементов ≤ 10 мс (бенчмарк в тестах на `palette-order.js`); виртуализация списка > 100 строк; ленивый `import()` модуля команд.
- `palette-order.js` остаётся **чистым** (без DOM); добавляются: `parseQuery(input) → { mode, command, args, rest }`, `rankCommands`, `chordMatcher` (конечный автомат аккордов), `frecency(entry, now)`.
- Юнит-тесты: парсер префиксов, ранжирование с алиасами на 6 языках, аккорды (таймаут, сброс при неверной клавише), пошаговые аргументы, права (viewer не видит мутирующие команды).

### 5.8 Критерии приёмки

- [ ] Сценарий «рестарт сервиса → просмотр логов → запуск бэкапа → переход в `/var/log`» выполняется **только с клавиатуры** за ≤ 15 нажатий.
- [ ] Viewer не видит и не может выполнить мутирующие команды (проверка и на клиенте, и на сервере).
- [ ] Аккорды работают на RU/ZH-раскладке; не срабатывают в input/textarea/xterm/редакторе.
- [ ] Полная поддержка скринридера (проверка по чек-листу ARIA), 6 тем, 6 языков.

## 6. Фича 5 — Интерактивные алерты Telegram / Discord

### 6.1 Суть и ценность

Алерт приходит с кнопками: **[🔄 Перезапустить] [📜 Логи] [🩺 AI-разбор] [❌ Игнорировать]**. Падение сервиса в 3 ночи решается одним нажатием в телефоне, без входа в админку.

### 6.2 Каналы и транспорт

| Канал | Механизм кнопок | Входящий транспорт |
|---|---|---|
| **Telegram** | `reply_markup.inline_keyboard` в `sendMessage`; нажатие → `callback_query` | `setWebhook` на `{PUBLIC_URL}/api/interactive/telegram/:channelId/:secret` с `secret_token` (заголовок `X-Telegram-Bot-Api-Secret-Token`), **или** long-polling `getUpdates` как режим для серверов без публичного HTTPS-адреса |
| **Discord** | Message Components (`components: [{type:1, components:[{type:2, style, label, custom_id}]}]`) | **Interactions Endpoint URL** `{PUBLIC_URL}/api/interactive/discord/:channelId`; обязательная проверка подписи **Ed25519** (`X-Signature-Ed25519`, `X-Signature-Timestamp`) через `crypto.verify(null, …)` с публичным ключом приложения (встроенный `node:crypto`, 0 зависимостей); ответ `PONG` на `PING` |

Существующие каналы `telegram`/`webhook`/`email` остаются; интерактивность — **опция канала** (`config.interactive = true`) и новые поля: для Discord — `applicationId`, `publicKey`, `botToken` (отправка сообщений с компонентами идёт через бота, `POST /channels/{id}/messages`; для простого webhook-канала кнопки недоступны — так устроен Discord).

### 6.3 Безопасные одноразовые токены кнопок

Кнопка **не содержит** параметров действия в открытом виде. `callback_data` (Telegram, ≤ 64 байта) / `custom_id` (Discord, ≤ 100) = `ea1.<tokenId>` — **непрозрачная ссылка** на запись в БД.

Свойства токена (`interactive_tokens`, §7):

| Свойство | Реализация |
|---|---|
| Непредсказуемость | 144 бита `crypto.randomBytes(18)` → base64url (24 символа) |
| Хранение | Только `sha256(token)`; исходный токен существует лишь в сообщении мессенджера |
| **Одноразовость** | Атомарное погашение: `UPDATE interactive_tokens SET used_at=?, used_by=? WHERE token_hash=? AND used_at IS NULL AND expires_at>?`; `changes===1` → допускается, иначе «уже использовано/истекло» |
| TTL | По умолчанию 30 минут для `restart/logs`, 24 ч для `ignore`, 10 мин для `confirm` (настраивается) |
| Привязка | К действию (`action`), цели (`panel/project/service`), каналу (`channel_id`), чату (`chat_id`), сообщению (`message_ref`) и **событию алерта** (`event_id`) |
| Привязка к исполнителю | Для Telegram: `from.id` должен быть в списке `allowed_user_ids` канала (иначе отказ + запись в `audit`); для Discord: `member.user.id` в `allowed_user_ids` **или** наличие роли `allowed_role_ids` |
| Группа токенов | Все кнопки одного сообщения имеют общий `group_id`; при погашении «опасной» кнопки остальные опасные деактивируются (защита от двойного рестарта) |
| Защита от повтора | Идемпотентность: повтор нажатия не выполняет действие повторно; пользователю — «Уже выполнено в 03:12» |
| Отзыв | При закрытии инцидента (`service` снова `ok`) все токены события инвалидируются |
| Подтверждение опасных | Для `risk ≥ medium` нажатие порождает **второе** сообщение с кнопками `[✅ Подтвердить] [Отмена]` (новый токен, TTL 60 с) |

### 6.4 Набор действий кнопок

| Кнопка | Действие (реестр §1.3) | Ответ пользователю |
|---|---|---|
| 🔄 **Перезапустить** | `service.restart` (для `panel_down` — недоступна; для `disk_high` — кнопка «🧹 Очистить» → `serverdoctor.smart_clean`) | Редактирование исходного сообщения: «🔄 Перезапуск… ✅ Сервис работает (12 с)» с итоговой проверкой состояния через 30 с |
| 📜 **Логи** | `service.logs_tail` (последние 30 строк, **редактирование секретов** `redact()`, обрезка ≤ 3500 символов для Telegram / ≤ 1800 для Discord) | Новое сообщение с блоком ```` ``` ````; при большем объёме — ссылка на UI (через сессию, не токен) |
| 🩺 **AI-разбор** | `ai.diagnose` → краткий вердикт (причина + 1–2 шага, ≤ 800 символов) | Сообщение; кнопка «Применить» **не** предлагается в чате — только в UI |
| ❌ **Игнорировать** | `alert.mute` на настраиваемое время (1 ч / 24 ч / до восстановления) для данного `panel+service+event_type` | Правка сообщения «🔕 Заглушено до 04:12 (@user)» |
| ✅ **Принять (ack)** | Пометить инцидент «в работе» | Имя ответственного в сообщении |

Telegram: после нажатия обязательно `answerCallbackQuery` (иначе «часики» на кнопке) и `editMessageReplyMarkup` — кнопки удаляются/заменяются статусом. Discord: type 7 (`UPDATE_MESSAGE`) или type 4/5 (deferred) в пределах 3 с (долгие действия — `DEFERRED_UPDATE_MESSAGE` и последующий `PATCH /webhooks/{app}/{token}/messages/@original`).

### 6.5 Модель прав для действий из мессенджера

- Канал в настройках получает **роль-потолок** (`viewer` — только 📜/❌; `operator` — + 🔄/🩺; `admin` — + рецепты Server Doctor). Действие допустимо, если `risk` ≤ потолка канала **и** исполнитель в allow-list.
- Область: канал привязывается к набору панелей (`panel_ids`); токен для чужой панели не выдаётся.
- Нажатия пишутся в `audit` с `username = 'telegram:<@username|id>'` / `'discord:<id>'`.
- Rate limit на исполнителя: ≤ 10 действий/мин, на канал ≤ 30/мин.

### 6.6 Защита входящих вебхуков

1. Telegram: проверка `X-Telegram-Bot-Api-Secret-Token` (константное время) + проверка, что `callback_query.message.chat.id` равен `chatId` канала; путь содержит случайный `:secret` (128 бит) — двойная защита.
2. Discord: проверка подписи Ed25519 по сырому телу **до** JSON-разбора; отклонение при расхождении времени `> 5 мин` (anti-replay); `401` на неверную подпись (требование Discord).
3. Эндпоинты помечены `public` (без сессии), но проходят через общий rate-limit (§3.7) и имеют лимит тела 64 КБ.
4. Ответ на любые ошибки аутентификации — одинаковый `401/404`, без деталей.
5. Идемпотентность по `update_id` / `interaction.id` (таблица недавних идентификаторов на 10 мин) — защита от повторной доставки.

### 6.7 Настройка (UX)

Настройки → Уведомления → канал → «Интерактивные кнопки»: пошаговый мастер — (1) проверить `EASYADMIN_PUBLIC_URL` (HTTPS), (2) вставить токен бота / данные приложения Discord, (3) нажать «Подключить» (EasyAdmin сам вызывает `setWebhook` / показывает URL для Discord Interactions Endpoint), (4) «Отправить тестовый алерт с кнопками», (5) указать разрешённых пользователей (кнопка «Определить мой ID»: пользователь пишет боту `/start`, EasyAdmin показывает захваченный `from.id` для подтверждения).

### 6.8 Расширение `alerts.js`

- `emit(event)` получает `event.id`, `event.target = { panelId, project, service }` и `event.actions = ['restart','logs','ai','ignore']` (по типу события).
- `sendTo` для интерактивных каналов вызывает `interactive.buildMessage(channel, event)` → создаёт группу токенов и формирует разметку; для обычных — поведение без изменений (обратная совместимость).
- Таблица соответствия событий и кнопок: `service_down` → 🔄 📜 🩺 ❌; `panel_down` → 📜(диагностика соединения) ❌; `disk_high` → 🧹 ❌; `overload` → 🩺 ❌; `backup_failed` → ▶️ «Повторить бэкап» 📜 ❌.
- Для остальных событий кнопка «❌ Игнорировать» опциональна.

### 6.9 Критерии приёмки

- [ ] Повторное нажатие той же кнопки не вызывает второго рестарта (e2e + гонка из 20 параллельных запросов → ровно 1 исполнение).
- [ ] Просроченный/чужой/подделанный токен → отказ, запись в `audit`.
- [ ] Discord: неверная подпись → `401`; корректный `PING` → `PONG`.
- [ ] Пользователь вне allow-list не может выполнить действие, даже получив `callback_data`.
- [ ] Логи в чате не содержат секретов (используется `redact`).
- [ ] Без `EASYADMIN_PUBLIC_URL` интерактивность недоступна, обычные алерты работают как раньше.

## 7. Модели данных SQLite

### 7.1 Правила миграций

- Миграции — в `src/db.js` в том же стиле: `CREATE TABLE IF NOT EXISTS` для новых таблиц и `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` для расширений. Версия схемы фиксируется в `settings` (`schema_version`), для упорядоченных многошаговых миграций — массив `MIGRATIONS = [{ v, up(db) }]`, выполняемый внутри `BEGIN IMMEDIATE … COMMIT`.
- Только аддитивные изменения (P4). Перед миграцией, затрагивающей данные, — автокопия БД (`VACUUM INTO 'easyadmin.db.pre-vN'`) — механизм бэкапа данных уже есть в `data-backup.js`.
- Все временные метки — `INTEGER` миллисекунды Unix (как в существующих таблицах). Все секреты — `*_enc` (`crypto.js`).
- Новые таблицы нужно добавить в **список бэкапа/восстановления** (`data-backup.js`/`data-restore.js`) и в `backups.test.js`.

## 8. Спецификация REST API

### 8.1 Соглашения

Совпадают с существующими: JSON, `Content-Type: application/json`; ошибки `{ "error": "сообщение", ... }` через `HttpError`; сессионная cookie; мутации требуют CSRF-защиты текущего механизма; опции маршрута `{ admin: true }`, `{ public: true }`, `{ hook: true }`. Роли: **V** = viewer, **O** = operator, **A** = admin; «+доступ к панели» = `canPanel`.

Коды: `400` валидация · `401` не авторизован/неверная подпись · `403` нет прав · `404` · `409` конфликт/уже выполнено · `413` · `422` недопустимое действие вне белого списка · `429` лимит · `502/504` внешний сервис.

## 10. Сквозные требования

### 10.1 Тестирование

| Уровень | Что | Инструмент |
|---|---|---|
| Юнит | `redact`, `fingerprint`, расчёт аптайма, парсеры `df/free/smartctl/journalctl`, ранжирование/аккорды палитры, генерация/погашение токенов, проверка подписи Ed25519, санитайзер SVG | `node --test` |
| Интеграция | SSE-пайплайн с поддельным OpenAI-совместимым сервером (в т.ч. рваные UTF-8 чанки, обрыв, таймаут); вебхуки Telegram/Discord с подписанными фикстурами; `runOnHost` со стабом | `node --test` + `node:http` |
| Безопасность | Fuzz параметров действий (`;`, `$()`, `` ` ``, `\n`, `..`, юникод), гонки при погашении токена, replay вебхука, prompt-injection-логи, SSRF (127.0.0.1, 169.254.169.254, `[::1]`, DNS-rebinding через повторное разрешение перед соединением) | `node --test` |
| Нагрузка | `/status`, `/status/badge/*` под самописным генератором нагрузки | `scripts/loadtest.js` (без зависимостей) |

### 10.2 Наблюдаемость

Метрики в существующий `/metrics` (токен `EASYADMIN_METRICS_TOKEN`): `easyadmin_ai_requests_total{provider,cached}`, `easyadmin_ai_tokens_total`, `easyadmin_status_requests_total{code}`, `easyadmin_status_ratelimited_total`, `easyadmin_doctor_runs_total{recipe,status}`, `easyadmin_doctor_freed_bytes_total`, `easyadmin_interactive_actions_total{action,result}`. Структурные записи в `audit` для всех мутаций.

### 10.3 Модель угроз (кратко, для `SECURITY.md`)

| Угроза | Митигация |
|---|---|
| Утечка секретов в LLM | `redact`, режимы приватности, прозрачный счётчик «что отправлено», локальные провайдеры |
| Prompt-injection из логов → вредные действия | Действия только из белого списка, параметры подставляет сервер, обязательное подтверждение человека |
| Инъекция команд в host-exec | Каталог команд в коде, whitelist-валидация, экранирование, фаззинг |
| DoS публичной страницы | In-memory снимок, ETag/304, rate-limit, глобальный предохранитель, лимиты парсера |
| Раскрытие инфраструктуры через `/status` | Whitelist-модель, публичные имена, тест-сниффер |
| Подделка/повтор кнопок Telegram/Discord | Секретный путь + заголовок/подпись, одноразовые хэшированные токены, TTL, allow-list, идемпотентность |
| XSS через логотип/инциденты/ответ ИИ | Санитизация SVG, CSP, рендер без `innerHTML`, markdown-light |
| SSRF через проверки/провайдеры/вебхуки | Схема-фильтр, блок приватных диапазонов с явными исключениями, отказ следовать редиректам |
| Эскалация прав через мессенджер | Потолок роли канала, allow-list исполнителей, подтверждение для `risk ≥ medium`, аудит |

### 10.4 Рост и «звёзды» (не функциональные, но входят в DoD)

- Для каждой фичи — **GIF ≤ 8 с** в `README` (палитра: рестарт с клавиатуры; Server Doctor: освобождение 20 ГБ; Status: публичная страница + бейдж; AI Doctor: потоковый вердикт + «Применить»; Telegram: нажатие «🔄» в чате).
- Раздел README «Why EasyAdmin» со сравнительной таблицей: Uptime Kuma / Portainer / Netdata / Beszel vs. EasyAdmin (**0 зависимостей, 1 процесс, 1 файл БД**).
- Шаблон issue/PR, `good first issue` для новых языков и провайдеров, `docker-compose` пример с Ollama (`docs/examples/ollama-compose.yml`).
- Демо-режим (`npm run demo`) расширяется: фиктивный AI-провайдер, наполненная страница статуса, имитация сбоя с интерактивными кнопками — чтобы любой мог оценить функции за минуту без реальных серверов.
